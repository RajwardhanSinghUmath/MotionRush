# Fresh capture and shutdown

`CaptureDevice` owns OpenCV in a spawned process. `CameraStream` polls a bounded shared-memory slot containing only the latest mirrored BGR frame, its sequence, measured receipt time and strictly increasing MediaPipe timestamp. Slower consumers skip overwritten frames. Images are copied under a publication lock; the parent acquires that lock with a timeout, so a stopped publisher cannot indefinitely block a read. IPC contains no frame queue or feeder thread. Oversized input is resized to fit 640 by 480 while preserving aspect ratio, and the image slot uses at most 921,600 bytes.

Reads explicitly report frame, waiting, stale, end, error or closed. Short waits preserve calibration and still let the preview process keys. Startup times out if no frame arrives. Terminal failure takes priority over a pending image. Frames older than 250 ms are discarded before inference; age is checked again after inference, by the independent session monitor and before every keystroke. Expiration disarms input and clears unusable tracking observations. A fresh frame alone never rearms the session.

One high-resolution monotonic receipt clock is used across acquisition, transport and input permission. The local Python 3.10 `monotonic` implementation was `GetTickCount64` with 15.625 ms resolution; `perf_counter` used `QueryPerformanceCounter` with reported resolution 100 ns. `camera.clock.now_ns` uses `perf_counter_ns`, whose Windows clock is shared across processes in the supported Python versions. [Python's time documentation](https://docs.python.org/3/library/time.html#time.perf_counter) describes that cross-process behavior. Reported clock resolution is not a claim of physical camera accuracy. Receipt is stamped before mirroring and resizing; sensor exposure and driver buffering remain unknown.

Shutdown first requests a normal stop and waits 250 ms, then terminates a still-blocked worker and waits 500 ms, with a final bounded kill/join fallback. The worker owns normal device release. Forced termination does not run its Python cleanup; the OS closes the stopped process's handles, and actual camera-device reuse still needs live hardware validation. The parent never releases an OpenCV device concurrently with its read. IPC is not reused after termination, since terminating a process can leave synchronization objects damaged, as described in [Python's multiprocessing documentation](https://docs.python.org/3/library/multiprocessing.html#multiprocessing.Process.terminate). These are configured wait limits, not hard real-time OS guarantees. Synchronous MediaPipe inference remains a separate possible hang in the main process.

Tests use spawned OpenCV capture on generated recordings, blocked-open and blocked-read fault devices, a held publication lock, worker death, stale images, oversized images, explicit end/error states, independent image copies and consumer backlog. Main-loop tests verify quit during a capture wait, no inference or keyboard output on stale capture, no command after a frame expires in inference, and preservation of calibration across a short wait. No test opens a physical webcam or injects native keyboard input.

`evaluation.benchmark_capture` runs checksum-verified original Weizmann videos through the actual capture process with actual pose inference. The final local run is recorded in `docs/benchmarks/capture-windows.json`; an earlier QPC run is retained in `capture-windows-prior-observation.json`. The earlier run experienced an inference stall that expired one frame and skipped eleven source observations. This is a performance limitation, not a successful accuracy result or a fixed model-runtime problem. The main-loop expiry test confirms such observations cannot issue commands. Results record tested module hashes and parent revision; they may predate the report's own commit.

The final Weizmann run observed all 125 standing and 42 jumping frames without a deliberate consumer delay. Adding 100 ms delay reduced observations to 38 and 13 while skipping 87 and 29 source frames; receipt age at read stayed below 94 ms. The simulated blocked read produced a 62.153 ms poll and a 278.277 ms forced shutdown, with no surviving worker. A separate original UCF101 FMP4 recording (320 by 240, approximately 29.97 FPS) observed 91 of 93 frames, skipping two, with maximum receipt age 22.673 ms and normal shutdown 135.113 ms; its report is `capture-windows-ucf.json`. These are local performance measurements and decoder checks, not gesture accuracy, hardware exposure timing or OS worst-case bounds.

Reproduce with `python -m evaluation.benchmark_capture --manifest evaluation/manifests/weizmann.json --data evaluation/data --file eli_wave1.avi --file eli_pjump.avi --consumer-delay-ms 0 --consumer-delay-ms 100 --fault-check --output evaluation/runs/capture.json`. Playback is paced from the original media FPS; it simulates camera delivery without measuring sensor exposure or live gesture-to-game latency. Frame skipping protects freshness but can miss short gestures, which requires broader temporal recognition and real-world validation.
