# Pose inference and responsiveness

The controller owns MediaPipe in a spawned process. Model initialization, inference and native cleanup happen there; none run in the preview loop. Capture, inference and global controls have separate owners. Offline evaluation can still use the synchronous `PoseEstimator` directly.

The parent publishes one latest request, containing copied BGR pixels and the original sequence, receipt time and strictly increasing source timestamp. The worker returns those same pixels and metadata together with extracted features and up to 33 landmarks. Requests overwritten while inference is busy are skipped. A response contains a bounded 32 KiB JSON payload and one image slot; nonfinite optional landmark fields become null. There are no transport queues or feeder threads. Both image slots are limited to 640 by 480 BGR, preserving aspect ratio when shrinking larger requests. Parent request/result lock acquisition waits at most 2 ms each; scheduling and copying can exceed nominal waits.

The preview draws returned landmarks on their source image. A cached fresh result may be displayed while waiting, but only a new result updates recognition, calibration and the input session. New camera activity cannot refresh an old pose's age. Source receipt age must remain within 250 ms when the response is read, when the main loop uses it, in the independent input guard and before each stroke. Stale results cannot issue commands. Expiration disarms the session, and later observations never rearm it automatically.

F7/C excludes observations captured before the calibration request. F8 waits up to one second for a pose captured after its request, while checking that the target still matches. Accepting that standing observation suppresses its own action, without swallowing the next new gesture. A later pause invalidates the pending arm. These checks use measured receipt/source timestamps, not an assumed frame increment.

Initialization has a 10-second deadline and each active inference a one-second deadline. A persistent result-lock failure also ends the worker session; one brief collision does not. Model failure, unexpected process exit or watchdog timeout pauses input and exits the controller through resource cleanup. There is no automatic restart or rearming. Settings live in `config/settings.py`.

Shutdown requests stop, waits 250 ms, then terminates a surviving process and waits 500 ms, with a final kill/join fallback of 500 ms. Normal shutdown lets the worker close the native model. A reported `native_close_completed` distinguishes completed model cleanup from termination during cleanup. Local original-video runs required forced termination before native close completed within the 250 ms grace period; normal native cleanup is not claimed for those runs. The OS reclaims process resources after termination. IPC is discarded and never reused after a forced stop. Configured waits are not hard real-time operating-system guarantees. [Python's multiprocessing documentation](https://docs.python.org/3/library/multiprocessing.html#multiprocessing.Process.terminate) explains that termination can bypass cleanup and damage synchronization objects.

Tests exercise correlated source pixels/features/timestamps, overwritten requests, expired inference, active blocked initialization/inference/close, native model loading inside a process, errors and shutdown. Main-loop checks verify cached poses are not processed twice, calibration rejects pre-request results, current camera frames cannot authorize expired poses, model errors release input and UI quit remains responsive during a deliberately blocked worker call. Native keyboard input and physical cameras are not used.

`evaluation.benchmark_pose_worker` measures actual production capture and pose processes using checksum-verified original videos. Model initialization finishes before media-FPS playback starts; first inference remains included. It polls every nominal 5 ms or with a declared consumer delay. It does not draw the preview, recognize gestures or deliver keyboard input. The report records module/model/source hashes and the parent revision, and may predate its own commit. `docs/benchmarks/pose-worker-windows.json` contains the final isolated measurement; the prior report is retained and identifies concurrent regression work during part of that initial observation.

In the final local Windows run, normal polling returned 121 fresh poses from 125 standing frames and 41 from 42 jumping frames, with median receipt-to-pose age about 47 ms and maximum below 70 ms. A declared 100 ms delay returned 47 and 16 poses, with median age about 140 ms and maximum 217.282 ms. No returned responses expired, but skipped observations remain missing and are not counted as successful recognition. Parent capture/submit/result polling stayed below 4.531 ms in these runs. The active blocked-inference surrogate produced its watchdog error while parent polling stayed below 0.177 ms, and shutdown took 271.741 ms. All workers were stopped. All four native-video runs used forced model shutdown before close completed; the measured pose shutdown times were 268–287 ms. These are observations on this machine, not upper bounds.

Reproduce with `python -m evaluation.benchmark_pose_worker --manifest evaluation/manifests/weizmann.json --data evaluation/data --file eli_wave1.avi --file eli_pjump.avi --consumer-delay-ms 0 --consumer-delay-ms 100 --fault-check --output evaluation/runs/pose-worker.json`. Controlled fault probes block a surrogate model, explicitly confirm entry into the fault and report polling and shutdown time. They do not force an internal MediaPipe hang. Transport timing and pose detection counts are not gesture accuracy, sensor exposure timing or live game acceptance. Skipping protects freshness but can miss short gestures; temporal recognition and broader player/game validation remain necessary.
