# Input scheduling without blocking the preview

The main loop starts an action sequence and polls its delivery state while continuing capture, pose consumption and preview controls. It never sleeps to hold a key or space two strokes. `KeyboardBridge.begin_action` returns an immediate result only when the sequence completes or fails immediately; otherwise `poll_action` returns one final immutable `DeliveryResult` later. Only that result updates the recognizer's expected game lane and completed-action notification. Recognition retains its pending sequence while delivery runs, so newer poses cannot queue commands behind it.

Each successfully inserted down edge starts a 20 ms minimum hold measured with the shared high-resolution monotonic clock. Each completed up edge starts a 30 ms minimum gap before another stroke. A poll advances at most one edge. If a poll arrives late, the next hold or gap starts from the actual edge time; there is no burst of catch-up events or compressed key timing. The overall sequence still takes its configured time, and late UI scheduling can lengthen it. The improvement removes that wait from the main loop rather than shortening the required key holds.

The scheduler has one active sequence and no command queue. It rejects simultaneous scheduled or synchronous submissions. Complete sequence validation happens before any down edge. Permission is checked at each poll, before each stroke and immediately before key down. A revoked permission cancels the sequence at the next poll without waiting for a hold deadline. An active hold is released and marked uncertain; a cancellation in a gap reports only already-completed strokes. Failed releases remain tracked and prevent new down events until release succeeds. An explicit release or close retains one cancellation result for the owner to acknowledge.

The main loop acknowledges cancellation before calibration, guide changes, lane reset or arming can replace recognition state. Exit and exceptions cancel delivery in a finally block, preserving completed lane strokes and releasing any active hold before worker teardown. F9 and focus/tracking loss also cancel unfinished delivery. A cancellation can leave game state uncertain, so the existing manual synchronization and F8 recovery procedure still applies. Native insertion success is not game acceptance.

The synchronous `send_action` API remains for offline callers and the before/after benchmark. It shares validation and native edge routines with scheduling; the production main loop uses `begin_action`, `poll_action` and `cancel_action`. Scheduler mutation belongs to the main-loop thread. The global control thread only revokes session permission, avoiding concurrent mutations of the key-delivery state. `SendInput`, foreground queries and OpenCV rendering are still synchronous calls; removing timing sleeps does not establish a hard upper bound on those operating-system calls.

Tests use a controlled clock and actual PyDirectInput event construction with native insertion mocked. They check minimum holds/gaps, late polling, edge order, pause during a hold/gap, completed prefixes, native failures, release recovery, queue rejection, immediate permission checks and exactly-once cancellation results. Full-controller tests show at least 25 pose updates are consumed during a triple-key sequence, quit releases an active hold, quit in a gap commits only completed lane steps, and calibration acknowledges cancellation before resetting state. The reviewed real-pose regressions are retained; no gesture threshold was changed.

`evaluation.benchmark_input_scheduler` records real timing waits and compares synchronous delivery against scheduled delivery, with `SendInput` mocked. The local ten-sample triple-key measurement recorded a blocking-call median of 155.144 ms. Scheduled calls had median 0.061 ms and maximum 0.830 ms, while full delivery still took about 156 ms. The largest scheduled call across all single/double/triple cases was 1.372 ms. Observed minimum holds and gaps remained above the configured 20 and 30 ms.

The benchmark also uses the actual production capture and pose processes on checksum-verified original videos. It initializes the model before media-FPS playback and inserts the same synthetic triple-key workload at the first available result at or after each 25-frame boundary. Input permission checks pose receipt age. It omits preview drawing, gesture classification and native target-window queries; input insertion remains mocked. Neither path opens a physical camera or delivers game input. The report records source/module/model hashes, Windows/Python versions and parent revision; it can predate its own commit.

On the original 125-frame standing clip, both paths completed five synthetic sequences. Synchronous delivery consumed 102 fresh poses, skipped 17 frames before capture consumption, and reached maximum pose age 202.468 ms and parent-iteration time 157.985 ms. Scheduling consumed 123 poses, captured all 125 frames without those skips, and measured maxima of 63.988 ms for pose age and 0.993 ms for the parent iteration. On the 42-frame jumping clip, both paths completed two sequences; pose results increased from 34 to 41, capture skips fell from six to zero, and maximum pose age fell from 188.566 to 74.486 ms. These are local pipeline observations under a declared synthetic input workload, not physical gesture accuracy or live-game latency. Timing variance and model transport can still skip observations.

The report is `docs/benchmarks/input-scheduler-windows.json`. Reproduce with `python -m evaluation.benchmark_input_scheduler --manifest evaluation/manifests/weizmann.json --data evaluation/data --file eli_wave1.avi --file eli_pjump.avi --samples 10 --output evaluation/runs/input-scheduler.json`. The comparison does not change frame freshness limits or tune gesture thresholds.
